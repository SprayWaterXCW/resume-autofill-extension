# 第一课：先建立 Agent 的闭环，再接入大模型

## 这一步在整个项目里做什么

你遇到的核心问题不是“模型能否说出这个字段应该填什么”，而是**模型的判断能否在变化的网页上可靠地变成结果**。网页可能先只有一张经历卡片；点击“添加”后才出现第二张。模型可能正确决定填写“毕业学校”，但控件在失焦后清空。若系统只执行一次批量填充，它会把“尝试过”误认为“完成了”。

因此我们先建立运行内核：

```text
当前页面状态 → 决策器提出下一步 → 工具检查并执行 → 再读页面 → 验证变化
       ↑                                                    |
       └──────── 失败反馈或任务尚未完成时继续 ────────────────┘
```

这就是 Agent 项目的骨架。模型以后决定“下一步是什么”，运行内核决定“允许做什么、做完是否真的生效”。这个分工与 [ReAct](https://arxiv.org/abs/2210.03629) 的交替推理和行动相呼应，也与 [Browser Agent](https://github.com/uiuing/browser-agent) 把模型、工具、执行和验证分离的设计相近。

## 技术一：把网页表示成 Observation

传统自动填表通常把网页扫描成一个字段列表，然后一次性处理。Agent 需要的是**可反复更新的状态**。我们定义一个观察结果，包含页面标识、经历区块、当前卡片数、每个字段的标签与位置、是否可写、以及可用控件。添加一张卡片后重新观察，字段列表就会变化。

本阶段的 `SyntheticFormEnvironment` 有 `reset()` 和 `step(action)`：`reset` 返回初始观察，`step` 执行一个动作并返回新的观察。这借鉴了 [BrowserGym](https://github.com/ServiceNow/BrowserGym) 的环境接口。好处是 Agent 内核不依赖 Chrome：同一套逻辑以后可以对接模拟页、本地 HTML 测试页或真实浏览器。

请注意**观察和事实真相的区别**：决策器读到的是经过整理的观察；任务是否成功由独立评判器基于环境里的真实状态判断。这样模型即使说“已完成”，也不能替代最终核对。

## 技术二：让决策器只提出结构化动作

`planner.decide(context)` 每轮返回一种 JSON 决策：

```json
{"kind":"act","tool":"add_entry","args":{"sectionKey":"educations"}}
```

或者：

```json
{"kind":"act","tool":"fill_field","args":{"fieldId":"field-1","sourcePath":"educations.0.school"}}
```

这与“让模型生成任意 JavaScript 然后在网页执行”有根本区别。决策器只表达**意图**，运行时掌握具体权限。模型不能指定自由文本作为待写值；它只能选资料库中已有的 `sourcePath`，工具在本地取值。也不能请求通用 `click`，因为这会让“添加经历”和“提交简历”共用危险能力。

目前 `ScriptedFixturePlanner` 是**模拟 LLM 的测试替身**，只认识这个虚构页面的标签。它不是最终的语义解决方案。第二阶段会换成真实模型，用未见过的字段名称测试它是否真的理解“毕业院校”和“毕业学校”对应同一资料。

## 技术三：用 Zod 建立工具契约

大模型可能输出不存在的工具名、漏参数、错参数，甚至把额外文本塞入参数。`contracts.js` 用 [Zod](https://zod.dev/) 定义动作参数；`registry.js` 在执行前先校验。`strict()` 会拒绝多余字段。此后才检查目标是否存在、控件是否安全、资料路径是否有效。

这是**能力边界**：允许名单中只有 `add_entry` 和 `fill_field`。输出 `submit_application` 会得到 `UNKNOWN_TOOL`，根本到不了页面环境。`add_entry` 还要求观察到的控件是 `type=button`，并且没有提交语义。第一阶段测试覆盖了模型提出提交、以及一个伪装成“添加经历”但 `type=submit` 的控件。

真实网站上，仅凭按钮文字和 HTML 类型仍不足以证明安全；后续 DOM 适配器必须检查实际元素与事件影响，在不确定时停止。这是禁止提交要求在架构里的位置，而不是一条只写在提示词中的口号。

## 技术四：后置条件与闭环恢复

一个动作的返回值只能说明“工具尝试过”。它不代表网页真的保存了结果。新内核对每个动作设定**后置条件**：

- `add_entry`：卡片数必须加一，并且有新字段出现。
- `fill_field`：重新观察后，目标字段值必须等于资料库中的预期值。

测试故意让页面吞掉第一次写入。工具执行时没有抛错，但回读仍是空值，于是轨迹记录 `POSTCONDITION_FAILED`。下一轮决策器看到字段未填，又尝试一次，最终通过验证。这个例子说明为何“点击成功”“input 事件已触发”和“用户最终看见正确值”是三个不同层次。

如果模型过早给出 `finish`，独立评判器仍能发现任务未完成，记录 `PREMATURE_FINISH`。每次运行还有 `maxSteps` 上限，避免错误循环无限耗费时间和费用。

## 技术五：基准任务与可观察性

`npm run bench` 当前有四个合成场景：正常两段教育经历、一次静默写入失败、模型提出提交、危险类型的“添加”控件。它分别统计任务完成和安全阻断，避免把“没有做坏事”算成“填表成功”。轨迹记录步骤、工具名、目标标识、验证结果和错误码，不记录简历实际值。

这只是**内核评测**。它不能证明新系统已经能处理真实招聘网站，也不能证明语义匹配能力。后续需要保留一批未参与开发的页面样例，单独测字段映射、重复经历、自定义下拉、错误恢复与禁止提交；还要与旧版或纯规则基线对比。这样简历上的技术结论才有可复核的证据。

## 隐私边界

`createCatalog()` 在本地保存 `path → value`；决策器只接收 `path/label`。页面原有值在发送给决策器前缩成 `filled` 布尔值。工具执行时才从资料库取出确切内容，写到页面。这样能减少资料暴露，但**未来接入 LLM 时可能有确需理解字段值的情况**，例如“英语流利”要在“良好／熟练”中选一项。到那时应定义最小必要数据和明确的脱敏／授权规则，而不是直接把整份真实简历塞进提示词。

## 自己动手看一遍

```sh
npm ci
npm run demo
npm test
npm run bench
```

先看 `demo` 的 5 步轨迹：1 次添加、4 次写值，全部通过后置条件。再读 `tests/agent-loop.test.js` 中“静默写入失败”的案例，对比失败轨迹和最后的 `completed`。最后对照 `src/core/runner.js` 和 `src/core/registry.js`，思考一个问题：如果下一步换成真实 LLM，哪些代码需要变，哪些安全和验证逻辑必须保持不变？答案是主要替换 `planner`，工具白名单、页面回读和独立评判仍由运行时掌握。
