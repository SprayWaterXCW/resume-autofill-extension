# 第二十七课：表单状态、执行后核验与覆盖模式

## 这一步在整个 Agent 中的位置

本步改进的是「执行 → 核验 → 继续规划」这一段。模型已经找到了资料来源，网页输入框也显示了答案，但网站的校验和预览仍可能认为它为空。执行器需要完成网页正常的输入与失焦流程，同时明确每项核验究竟证明了哪一层数据。

```mermaid
flowchart LR
  A[模型提出字段与资料路径] --> B[校验语义、来源与文档身份]
  B --> C[受限控件动作]
  C --> D[输入框回读]
  D --> E[输入组件状态核验]
  E --> F[重新观察与整页复核]
  F --> G[用户检查网站预览]
```

Agent 的自主程度来自根据执行结果继续观察和规划。这里的进步是让执行结果更可靠：网页没有接收答案时，下一轮必须看到失败，不能因为输入框里有字而把它排除为已完成。

## 1. 四层不同的值

以虚构的「实习说明」为例，网页可能同时存在以下四层数据。

| 层次 | 例子 | 能证明什么 |
| --- | --- | --- |
| DOM 控件 | `textarea.value` | 屏幕上输入框显示了什么 |
| 输入组件状态 | 输入组件自己的 React state | 输入组件是否接收了文字 |
| 业务表单状态 | 表单 model 或预览数据 | 网页校验、联动和预览使用什么 |
| 服务器草稿 | 保存后网站读取的资料 | 是否真正持久保存 |

旧执行器主要检查第一层。若程序只改了 DOM，组件和表单可能仍为空。进一步只证明组件接收了文字，也不能证明业务表单接收了它：真实页面中有组件在 `onChange` 更新自己的值，直到 `onBlur` 才通知表单。因此进入预览时仍可能提示必填。服务器保存又是单独的一层证据。

React 的受控输入把 `value` 交给组件状态管理，并通过 `onChange` 更新这个状态。因此修改 DOM 属性和完成组件输入是两件事。参考 [React 官方输入组件说明](https://react.dev/reference/react-dom/components/input)。

## 2. Chrome 的 ISOLATED 与 MAIN

扩展内容脚本通常运行在 `ISOLATED` 世界。它与网页共享 DOM，但 JavaScript 环境和对象属性视图与网页不同。扫描、字段绑定、资料凭据和受限执行留在这个环境中。

本步新增一个很小的 `MAIN` 世界函数，用网页所在环境完成原生输入，并读取当前控件上的状态证据。它的能力只有处理被本轮明确标记的一个输入控件。环境边界的官方说明见 [Chrome 内容脚本文档](https://developer.chrome.com/docs/extensions/develop/concepts/content-scripts)。

调用过程如下。

1. 隔离执行器检查目标身份、资料来源、权限和填写模式。
2. 给目标加上一次性的随机票据，私下保存目标绑定与期望值。
3. 后台只向任务绑定的标签页和 `documentId` 注入输入函数。
4. MAIN 函数再次核对网址、票据唯一性、控件类型和可编辑权限。
5. 隔离执行器核对返回的布尔证据、实际 DOM 和原绑定，移除票据。

真实资料值只在本地动作参数中短暂传递。返回日志仅保留布尔状态、适配器类型、字段 ID 和来源路径，不返回网页状态对象、React 属性、资料值或页面 URL。

这相当于一个受限动作协议：模型提出需求，程序确定动作的目标和范围。随机票据负责本次动作关联，标签页与文档绑定负责防止动作落到切换或刷新后的另一页。

## 3. 如何完成输入

对普通文本和多行文本，先尝试浏览器的编辑动作，产生页面能够处理的输入事件。浏览器不支持该动作、没有产生输入事件或结果不一致时，使用 MAIN 世界的原生 `value` setter 与冒泡的 `input/change` 事件。

浏览器编辑动作目前使用 `execCommand("insertText")`。这个 API 已弃用，所以它只是有检查的首选路径；失败时有原生 setter 回退。不能因为调用返回成功就假定网页状态更新。参考 [MDN 的 execCommand 说明](https://developer.mozilla.org/en-US/docs/Web/API/Document/execCommand)。

对已经被旧方式写入的控件，可能出现 DOM 与框架跟踪值一致、应用状态仍为空的情况。新执行器在明确观察到这种不一致时，通过原生 setter 与输入事件形成实际值变化，再写入资料值；不会修改 React 的跟踪器、fiber 或全局 store，也不会直接调用组件的回调函数。

之后调用控件原生失焦，并检查是否实际收到 `blur` 和 `focusout`。在扩展面板持有焦点、原标签页没有原生焦点时，调用 `.blur()` 可能没有形成这些事件。只有缺少事件时，才向这个已验证目标补发对应的标准 FocusEvent；原生事件已经发生就不再重复。`blur` 不冒泡，`focusout` 冒泡；React 的 `onBlur` 有冒泡语义。参见 [MDN focusout](https://developer.mozilla.org/en-US/docs/Web/API/Element/focusout_event) 与 [React 焦点事件](https://react.dev/reference/react-dom/components/common#focusevent-handler)。

0.7.27 的中间实测说明，组件值一致仍不足以通过网站预览。只读检查网站处理函数后发现失焦才向外层传递 `{value, text}` 或当前说明文字的链路。0.7.28 的真实日志同时记录 `documentFocused=false` 和 `syntheticBlurUsed=true`，与缺少原生失焦的诊断相符。这里记录事实与事件，不直接访问或修改业务表单 store。

日期弹层、地区树和自定义下拉仍采用各自经过观察的控件协议。普通文本的修复不能代替这些控件的选择、局部确认和关闭检查。

## 4. 后置条件与失败证据

成功回执同时要求以下条件。

- 文档和字段身份仍保持唯一。
- 实际控件回读与本次资料值一致。
- 原生校验没有发现无效值。
- 本次输入产生了事件。
- 如果能够观察受控输入组件状态，它也必须与资料值一致。

本步读取 React 当前宿主控件的属性作为只读状态证据，只返回 `pageStateObserved/pageStateMatched`。历史诊断键名保留，但本步明确把它解释为输入组件状态，不能当成业务表单或保存结果。这也依赖 React 的内部属性约定，不能声称适用于所有框架。面板区分「只完成控件选择或回读」与「已核对输入组件状态」，并提示网站预览仍需核对。

观察到状态但值不一致时，返回 `PAGE_STATE_MISMATCH`。整页结束审计再次读取状态；若后来被另一动作清空，撤销成功，返回 `FINAL_PAGE_STATE_MISMATCH`。最终审计是只读操作，不为了通过检查再偷偷填写。

输入组件核验不能代替业务表单和服务器保存验收。只有网站暂存并重新读取的行为提供了持久性证据，才可以写相应字段「暂存后保持」。当前 Agent 没有自动保存或提交功能，面板因此明确显示保存结果尚未验证。

## 5. 为什么填写模式需要贯穿整个任务

新增两个模式，默认「全部覆盖」。

| 模式 | 已有普通内容 | 没有资料来源 | 本轮已经核验的内容 |
| --- | --- | --- | --- |
| 全部覆盖 | 按资料库覆盖可编辑字段 | 保留，不清空 | 继续审计，不反复写入 |
| 只填空白 | 保留 | 保留，不清空 | 继续审计，不反复写入 |

只读、禁用、文件上传、声明、签名和提交等原有边界继续生效。覆盖模式不代表可以绕过控件权限。

模式保存在扩展本地。点击开始时，每个任务固定自己的模式；任务期间修改下拉只影响之后启动的任务。A 页以「只填空白」运行、B 页以「全部覆盖」运行时，它们互不改变。

同一个模式还进入规划上下文和快照指纹。候选生成、计划验证、执行前检查和 MAIN 写入边界都使用这个值，避免模型按一种策略规划、执行器按另一种策略操作。

「只填空白」还需要处理竞态：观察时为空，模型规划期间用户填入了文字。MAIN 写入前再次检查真实值，此时返回 `PROTECTED`，不会覆盖用户刚输入的内容。这是执行时前置条件，不能只在首次扫描时检查一次。

## 6. 测试如何避免再次验证错目标

本步加入真实 React 18 的虚构受控表单。它同时维护 DOM 和独立的预览数据，覆盖基本文本、实习公司、多行实习说明和校园说明。

测试先复现旧方式：只写 DOM，输入框有文字，预览数据仍为空。然后调用生产 MAIN 输入函数，断言预览数据实际更新，并运行结束审计。另一个组件故意拒绝状态更新；即使 DOM 有值，也必须失败。第三种情况是在写入后让组件状态丢失，同时保留 DOM 的假象，整页审计必须撤销成功。

进一步加入两层状态的 React 组件：`onChange` 只更新内部值，`onBlur` 才更新独立预览数据。测试既模拟缺少原生失焦，又检查正常失焦时不会重复通知；输入框和 textarea 都必须把完整文字交给预览数据。这条测试直接对应中间实测的缺口。

其他回归覆盖两种模式、空白模式的并发用户编辑、模式与快照绑定、每个标签页独立冻结偏好、禁止处理按钮和错误文档，以及日志不含私密值。

真实 Chrome 验收沿用用户已有的资料与模型，刷新后只点击正常开始按钮。网站验证与预览的实际结果单独记录，不能用虚构测试的通过数量替代。最新证据及仍未通过项见 [本步验收报告](../../reports/page-state-2026-10-06.md)。
