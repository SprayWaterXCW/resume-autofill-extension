# 第三课：在 Chrome 中看见 Agent 真正填写页面

## 这一步在整个项目里做什么

前两阶段的 `SyntheticFormEnvironment` 是内存中的表单：它能精确测试工具和验证逻辑，但看不到真实输入框怎样变化。本阶段增加了一张本地招聘页，并用 `DemoDomEnvironment` 把网页 DOM 接到**同一个** `runAgent`。你现在可以在 Chrome 左侧看到表单，在右侧看到 Agent 每一步的记录。

这一步完成的是“从抽象环境到浏览器页面”的第一次适配。它证明运行内核不依赖终端文本或内存假表单；还没有实现任意招聘网站的识别与操作。

## 如何读右侧执行记录

每一步都是可展开的卡片。最新一步默认展开；旧步骤可以点击查看。顶部的“本次目标”和“剩余待核对项”由程序计算。卡片内部按实际时间顺序更新：

1. **观察**：当前页面的经历卡片数、可见字段数和空字段数，来自 DOM 观察结果。
2. **判断**：模型或演示脚本给出的简短理由。它说明选择依据，不能当作事实证明；它不是模型内部逐字思维过程。
3. **准备**：本轮选中的受控工具、目标字段与资料路径，以及程序预期看到的变化。
4. **执行**：只有通过本地安全检查后，才显示“正在执行”；被阻断的动作明确标成“未执行”。
5. **核验**：重新读取页面后，显示卡片数变化或字段值是否与本地资料一致。失败会标明需要重试或停止。

决策摘要只在当前页面显示，不写入 Agent 的持久轨迹或下一轮模型历史。步骤卡片不保存资料实际值；如果摘要碰巧包含与本地资料值完全相同的文字，显示前会替换为“资料值已隐藏”。代码分别在 `src/core/runner.js`（阶段事件）、`src/llm/openai-compatible-planner.js`（简短摘要参数）和 `web-demo/step-log.js`（卡片呈现）。

```text
Chrome 中的招聘页
      ↓ observe：读卡片、标签、输入框、添加按钮
Agent 内核 → 决策器（脚本或 LLM）
      ↓ 工具白名单与参数校验
DOM adapter → 点击“添加教育经历”或写入一个输入框
      ↓ 重新 observe、核对页面状态
右侧进度和执行记录
```

## 技术一：DOM 是环境，观察与动作要分开

`web-demo/dom-environment.js` 实现了运行内核需要的 `reset()`、`observe()`、`step()`、`evaluate()`。`observe()` 从页面现有卡片中数出经历段数，读取每个输入框的标签、位置和值，并记录“添加教育经历”按钮的类型。它返回结构化观察；模型只看到其中的标签、位置与是否已填，看不到输入框的真实值。

`step()` 只认识两种动作：`add_entry` 点击本地添加按钮，`fill_field` 从本地资料目录取值并写入一个已观察到的输入框。写入后触发页面的 `input` 和 `change` 事件，以模拟正常表单交互。然后它再观察 DOM；运行内核验证：添加动作确实多了一张卡片，填写动作确实使目标输入框成为预期值。**模型提出动作不等于动作成功**，页面回读才是证据。

`evaluate()` 是独立的任务判定器。它检查两段经历的四个值、卡片总数和提交计数，不接受模型一句“完成了”作为成功。当前资料全是 `src/fixtures/synthetic-form.js` 中虚构的学校与专业；没有导入旧版真实简历。

## 技术二：浏览器和模型服务分工

浏览器直接持有页面 DOM，因此它运行 `runAgent`、DOM adapter 和本地资料目录。真实模型的 API Key 只加载到 `web-demo/server.js` 的 Node 进程中。浏览器把**去掉资料值**的上下文发给本机 `/api/decide`，Node 服务再请求用户配置的模型，并只把结构化决策返回浏览器。

服务监听 `127.0.0.1:4173`，检查 `Host`、`Origin` 和 JSON 类型。页面的 Content Security Policy 将脚本、样式和网络连接限制在本地源，同时设置 `form-action 'none'`。演示页没有提交接口，所谓“提交申请”只是禁用的展示按钮；工具注册表也没有提交动作。

浏览器和服务都运行在你的电脑上，但模型 API 仍是外部服务。模型会收到虚构页面的字段名称、按钮文字、资料路径及少量动作历史。模型调用可能产生费用。

## 技术三：模型一次给多个工具调用时怎么办

实际跑 `deepseek-flash` 时，第一轮响应的安全诊断显示 `finishReason=tool_calls`、`toolCallCount=2`。这不是页面错误，而是模型一次提出了两个动作。根据 [DeepSeek Chat Completion 文档](https://api-docs.deepseek.com/api/create-chat-completion/)，一次响应可以包含多个 `tool_calls`。

运行时仍遵守“一轮只执行一个动作”：只有所有建议都是参数有效的 `add_entry` 或 `fill_field`，才执行第一个，丢弃其余建议。执行后重新读取页面，再向模型询问下一步。这样后一条建议不会拿着旧的字段 ID 在变化后的页面上执行。如果其中含未知工具、`halt`、`finish` 或无效参数，整轮拒绝。自动测试覆盖了安全的多建议执行和混入未知提交工具的拒绝。

## 如何亲自观察

在项目根目录运行 `npm run demo:web`，然后用 Chrome 打开 <http://127.0.0.1:4173>。

1. 初始页面只有一张教育经历卡片，资料目录有两段。
2. 点击「快速演示」，看 Agent 新增卡片并填完四个字段；这个模式不调用 API。
3. 点击「重置表单」，再点击「真实模型填写」；这个模式由 `.env.local` 配置的 LLM 选择动作。
4. 对照左侧的输入框、右侧的 `4 / 4` 进度和逐步记录。每条成功记录都表示动作之后完成了页面回读。

关闭终端服务用 `Ctrl+C`。刷新网页也会恢复为一张空卡片；演示结果不持久化。

## 这一步能证明什么，下一步是什么

本阶段证明：同一 Agent 内核可以驱动真实 Chrome 页面中的 DOM，模型能在这张虚构招聘页上根据“毕业院校／毕业学校”的不同叫法选对字段，并补足第二段经历。它还证明密钥留在本机服务、安全工具白名单仍然生效。

下一步需要把 DOM adapter 扩展到更多控件与区块，加入可复现的浏览器任务集，再考虑真正的 Chrome 扩展或浏览器自动化适配层。真实网站会有动态下拉框、校验、弹窗和不同页面结构；当前演示的成功不能替代那部分评测。
