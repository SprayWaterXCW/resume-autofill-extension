# 第十七课：模型返回与上下文预算

## 这一层在 Agent 中的位置

页面观察 → 建立候选视图 → 请求模型 → 解析结构化返回 → 检查语义与来源 → 执行工具 → 回读。

本轮的真实故障发生在解析结构化返回处，尚未进入工具执行。要判断这一类故障，需要分别记录“模型有没有调用函数”“参数能不能解析”“字段格式是否正确”，然后才能讨论后面的语义和控件。

## 1. 结构化输出有多层失败

函数调用包含函数类型、名称以及 JSON 参数字符串。解析至少有以下边界：

| 边界 | 失败例子 |
| --- | --- |
| 工具调用存在 | 只返回一段文字 |
| 工具数量和类型 | 返回两个调用或不允许的函数 |
| 输出完整 | 提供商标记 length，参数被截断 |
| JSON 语法 | 字符串少了结束括号 |
| 参数 schema | 不存在的角色、额外 value 属性、错误类型 |
| 映射语义 | 字段和来源合法，但把名称映射到详情 |

Zod 负责参数格式，buildFillPlan 负责已知引用、语义、记录顺序和页面策略。两者要分别产生诊断。捕获异常后只输出统一错误码，会丢失修复需要的信息。

## 2. 如何记录错误而不泄露响应

模型可能在错误返回中带入不应保存的文字。诊断使用固定字段和有限枚举：阶段、finishReason、调用数量、参数字符数、输入输出 token 数、问题路径与实际类型。

例如：

```json
{
  "code": "invalid_value",
  "path": ["fieldMappings", 0, "semanticRole"],
  "actualType": "string"
}
```

这里只知道角色格式不合格，不保存它具体返回了什么。未知属性名也只记录数量。诊断在服务端、客户端及发给下一轮模型的反馈中都重新校验，避免一次脱敏后又被别的层加入原文。

## 3. 修复循环也需要边界

原来的修复循环覆盖语义和引用错误，格式错误直接结束。现在返回格式错误也使用最多三次的同一循环：

1. 解析失败，记录封闭诊断。
2. 重新观察，检查页面是否变化。
3. 把诊断作为反馈，请模型重新给出契约内提议。
4. 返回有效后，仍经过完整的来源、语义和记录校验。
5. 三次仍不合格则停止。

格式错误没有可执行的部分计划。不能截取不完整 JSON 的前半段去填写，也不能把模型正文当作浏览器操作。

## 4. 为什么清单重复会影响规模

给每个字段列出整个资料目录，输入大小会随字段数和资料数的乘积增长。57 字段、201 路径的虚构请求在重复清单下用了约 10.7 万输入 token，小模板没有暴露这类问题。

新版在函数契约分支中保留来源白名单，描述只列可用角色。普通资料不需要获奖专用角色；可选 null 作为属性未提供处理。这样减少重复数据，同时保留程序复验。

## 5. 候选视图与完整状态

完整观察是程序复核的依据；模型输入是为当前决策准备的视图。

候选视图只包含待处理字段、可能使用的来源，以及投影的递归来源关系。profileSections 保留各区块的完整记录数。已有内容和手工声明等字段仍存在于本地完整观察中，用于保护、布局判断和最终检查。

snapshotId 对应完整观察。模型只需原样返回它，程序随后按完整快照验证。卡片缺口由完整资料计算，候选裁剪不会把第六条经历从本地资料删除。

在只有一个空字段的规模用例中，模型仅看到该目标和它的候选来源，输入降到约 2900 token。这既减少成本，也降低把无关来源混入映射的机会。

## 6. 验证需要匹配实际风险

模型规模用例检查空白与已有内容两种环境。格式恢复测试检查错误期间动作数为 0、反馈历史保留及页面变化中止。WebSocket 测试检查诊断确实能到达用户复制的执行记录。

另外，严格路径相等不能替代控件结果验证。陌生等级下拉使用 level 时，需要观察选项，按范围或等次选择，再比较预期值。本轮保留了模型严格评分 5 / 6 的报告，额外用同一页面执行器验证这个等级投影的结果。

145 项回归与两个规模规划通过说明这次程序修改有对应证据；原真实失败子原因已被旧日志丢弃，仍需新版诊断判断后续实际问题。
