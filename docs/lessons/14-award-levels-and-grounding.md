# 第十四课：获奖级别、数据绑定与控件语义

本课记录 0.7.1 的实现过程。0.7.2 已将文本加元数据的编辑方式改为四字段、可增删的结构化记录；当前数据模型和使用方式见[第十五课](15-structured-award-records.md)。

这一轮解决的是：资料里保存了奖项，网页却还有国家级、省级、一等奖等字段需要填写。我们把用户维护的事实、模型提出的映射和浏览器实际选项接通了。

## 1. 级别与等次是两个独立维度

| 字段 | 回答的问题 | 例子 |
| --- | --- | --- |
| 获奖级别 scope | 这个奖项的获奖范围是什么？ | 国家级、省级、市级、校级 |
| 获奖等次 rank | 在这个奖项中获得什么奖等？ | 一等奖、二等奖、金奖、优秀奖 |

国家级本身不能说明获得了一等奖，金奖也不会自动换算为一等奖。名称中出现“全国”不能直接证明某个具体奖项的正式获奖级别。系统将范围留为“未确认”，用户根据证书或通知补充。

原文明确写出的“省级”“二等奖”可以用确定性解析提取，页面会显示提取提示。出现冲突、否定或含糊文字时保持空值。这些规则不证明证书真实性，它们只保留用户已提供的资料依据。

## 2. 为什么保留原文，同时增加结构

旧资料中的获奖和竞赛是文本，用户已有的描述与导入格式需要保留。新的私有 profile 增加 awardDetails，在每条原文旁边记录 scope、rank、信息来源及关联信息。原文仍保存在 additional 中，证书分类不变。

用户修改资料时，资料编辑器、导入器、保存器都调用同一份 normalizeAgentProfile，保证这份扩展数据经过保存、重开和备份导入仍在。单独调用旧 ResumeSchema 的归一化会丢弃未知属性，因此 Agent 在旧 schema 外增加明确的归一化入口。

这一步叫数据建模：先定义系统实际需要表达的事实及其关系。增加一个网页输入框只有在存储、导入、事实目录和执行器都理解它时才构成完整功能。

## 3. 条目绑定：为什么不能只记数组下标

假设虚构奖项甲位于第 1 条，用户把它移到第 2 条。若国家级只保存在“第 1 条”的下标，重排后就会写到另一个奖项上。

本轮使用规范化原文匹配对应记录，再将级别和等次移动到当前位置。删除其他记录不影响这条绑定。用户改变原文后，旧级别和等次需要重新确认；原文中明确保留的级别/等次仍可重新提取。

完全相同原文用出现序号与重复数量区分。增删重复条目后，系统使旧确认失效，避免任意选择一条。若两项原文相同但级别不同，建议在原文中补上年份或类别，让它们可区分。当前机制没有独立的奖项对象 ID。

这一步涉及稳定身份和关联。网站卡片的 entryIndex 只是当前页面位置，资料记录的身份与位置需要分别处理。

## 4. 事实目录与本地投影

资料保存后，Agent 可以使用这些路径：

```text
awards.0.name    名称与原文
awards.0.scope   获奖级别
awards.0.rank    获奖等次
awards.0.level   按选项区分级别/等次的本地投影
```

scope 或 rank 没有值时，不会生成可填写的来源。至少有一个明确来源，才生成 level。derivedFrom 列出真实存在的父路径；level 的存在不代表两个维度都已填写。

模型收到标签、路径、记录索引和确认状态。私有值由本地事实库保存。level 的私有载荷同时携带这条记录已有的级别和等次，只有选项执行器解析它；它不能写入文本框，也不会出现在模型请求或执行日志中。

投影的作用是为目标控件准备一种使用方式，同时保留来源。它没有增加一条新的获奖经历，记录池的数量仍按原奖项计算。

## 5. “获奖等级”的现场含义如何确定

| 已观察目标 | 使用的资料 |
| --- | --- |
| 明确的“获奖级别”“获奖范围” | 同条记录的 scope |
| 明确的“获奖等次”“获奖名次” | 同条记录的 rank |
| “获奖等级”下拉或单选 | level，打开选项后确定所需维度 |
| 含糊的“获奖等级”文本框 | 留待人工，不能从选项获得依据 |

执行器对等级选项执行以下步骤：

1. 核对字段、分组及当前文档，保护已有内容。
2. 打开绑定的下拉；等待延迟渲染的候选。
3. 判断选项属于范围还是等次。两类混在一起、未知含义或没有选项时不选择。
4. 取同条记录对应维度的已确认值，寻找唯一选项。
5. 点击该选项，检查主字段显示、菜单关闭状态。
6. 保存本轮写入凭据，在后续操作和结束时重新回读。

国家级可以对应明确的“国家”“全国”选项；如果网站同时提供两个等价候选，系统无法唯一选择。金奖不会匹配一等奖。读取到候选、点击了候选、控件提交了选择是不同状态，只有完成回读核验才算成功。

这一步属于 Agent 的 grounding：把计划绑定到已有资料、实际观察和明确动作结果。网页标签存在歧义时，需要执行阶段的新观察。

## 6. 获奖与竞赛的记录池

网站只有获奖区块时，记录顺序是所有 awards，接着所有 competitions。例如一个奖项和一个竞赛，网页第二张卡片使用 competitions.0，级别与等次也从同一条记录取。

网站同时有获奖与竞赛区块时，两个记录池分开。模型提出映射后，程序重新校验来源前缀、位置、字段语义和重复引用。

真实模型验证曾发现两个错误：漏掉合并后的竞赛；将 level 用在明确的级别字段。修复后，工具的 JSON Schema 按字段列出符合维度及明确记录位置的来源。缺少 scope 的字段不能在工具契约里选择 level 代替。模型仍负责其他语义关联；运行时的独立校验继续生效。

## 7. 日志如何帮助下次调试

日志新增以下诊断，记录代码和维度，不记录奖项内容或选中值：

| 代码 | 含义 |
| --- | --- |
| AWARD_SCOPE_MISSING | 控件要求级别，但用户尚未确认 |
| AWARD_RANK_MISSING | 控件要求等次，但资料没有填写 |
| AWARD_LEVEL_AMBIGUOUS | 实际选项无法明确区分维度 |
| AWARD_OPTION_AMBIGUOUS | 同义候选超过一个 |
| AWARD_OPTION_UNAVAILABLE | 没有对应选项 |
| AWARD_AXIS_MISMATCH | 观察到的选项与映射维度不一致 |

界面会给出中文解释，例如“该控件要求获奖级别，资料尚未确认，请在资料页补充”。其他字段继续执行，失败字段留待核对。

## 8. 验证与使用

```sh
npm test
npm run build:extension
npm run eval:awards -- --output=reports/award-levels-model-2026-10-05.json
```

本轮 126 项本地测试通过，包括保存重开、备份、原文保留、重排删除、重复条目、未知级别、合并记录、错误映射、延迟下拉、菜单关闭和最终回读。真实模型的三个虚构映射案例通过 3/3。它们验证映射能力，真实招聘页的控件仍需用户补齐级别后验收。

普通 Chrome 中已更新 0.7.1，通过工具栏打开资料页，检查原有 5 条获奖和 5 条竞赛均显示独立级别与等次，七种级别选项可见。界面检查没有修改用户资料。

使用时进入「编辑资料 · 打开网页 → 补充信息」，为每条填写级别和等次，核对自动提取的值，点击「保存资料」，再回到招聘网页运行。资料编辑不需要模型服务，开始填写需要本机服务。
