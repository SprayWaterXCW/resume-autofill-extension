# 第十五课：把获奖与竞赛变成可编辑的结构化记录

## 1. 这一轮解决什么

上一版仍然通过整段文本确定有哪些奖项，下方卡片只补充级别和等次。用户想修改名称、增加一条或删除一条时，需要回到大文本框操作。现在两类经历都直接填写四个字段，卡片可增删，名称可自由编辑。

这一步位于整个 Agent 的资料来源层：用户维护事实，模型根据字段标签选择事实路径，受限浏览器工具按路径取值并回读。资料结构决定了模型能够选择哪些独立答案。

## 2. 正式的数据结构

每份私有 profile 包含 awardRecords，版本为 1。awards 和 competitions 分别是数组，每条记录包含：

| 属性 | 含义 | 进入模型的形式 |
| --- | --- | --- |
| id | 稳定 UUID，供编辑器定位记录 | 不进入模型 |
| name | 奖项或竞赛名称 | 路径和标签 |
| scope | 国家级、省级等范围 | 路径和标签 |
| rank | 一等奖、二等奖等实际等次 | 路径和标签 |
| description | 详细信息 | 路径和标签 |
| legacyText | 旧数据迁移时保留的原文证据 | 不进入模型，也不用于填写 |

例如，第 1 条获奖有 awards.0.name、awards.0.description 等事实路径。名称与详情分别保存，因此网页上“奖项名称”和“详细信息”能够使用不同来源。空字段不产生可用事实。

## 3. 为什么需要稳定 ID

数组位置会因为删除记录而变化；奖项名称也允许修改。同名奖项还可能有不同年份或等次。编辑器用稳定 UUID 找到正在编辑的记录，而不是根据名称或旧下标寻找级别。

这属于数据建模中的“记录身份”：用户改名时保留身份，添加时创建新身份，删除时移除整条记录。Agent 的事实路径仍按当前数组顺序生成，已有的记录池校验继续负责网页第几张卡片对应哪条资料。身份管理与网页记录顺序分别有清晰的用途。

## 4. 如何迁移旧数据

旧插件的 JSON 和 0.7.1 的备份仍能导入。旧条目第一行迁入名称，其余行迁入详情；单行内容完整保留在名称里，用户可直接调整。完整原文另保存在私有迁移证据中。

0.7.1 手工填写的级别、等次按旧版原文关联规则迁入。旧文明确写出的等级可提取，不从竞赛名称推断国家级或省级。迁移只在没有结构化记录时进行；已有结构化数据即使数组为空，也以该数组为准。用户删除全部奖项后，旧文本不能把它们重新恢复出来。

这属于向后兼容的数据迁移与幂等规范化：同一份已经迁移的资料再次加载，不会创建新条目或改换已有 ID。加载迁移在内存中进行，点击保存后写入 Chrome 的本地资料。

## 5. 模型建议怎样受到约束

名称字段只允许名称来源，详情字段只允许详情来源，级别只允许 scope，等次只允许 rank。模型的工具 JSON Schema 列出每个已观察获奖字段的可选来源，本地计划检查再次复验，执行器也独立拒绝把名称写进详情。

含糊的“获奖等级”下拉仍使用 level 本地投影。工具打开实际选项后，区分该网站在问范围还是等次。这个投影不会代替明确的“获奖级别”来源。

本轮真实模型的首次虚构测试有一次混淆 scope 与 level，计划校验拦截了它。增加逐字段来源说明后，三个案例通过。测试结果证明这次映射有效；运行时仍保留校验与有限重试，不能把单次通过看作所有模型输出必然正确。

## 6. 用户怎样使用

1. 点击普通 Chrome 的 Resume Agent 图标。
2. 点击“编辑资料 · 打开网页”，进入“补充信息”。
3. 每条直接填写名称、级别、等次、详细信息。
4. 通过“＋ 添加获奖”“＋ 添加竞赛”增加条目，或“删除本条”移除条目。
5. 点击“保存资料”。下一次填写从这些结构化记录建立事实库。

只有获奖区块的网站继续合并获奖和竞赛；同时存在两类区块时分别填写。真实招聘页的具体控件效果仍需按网站验收。本轮验证记录见[验证报告](../../reports/structured-awards-2026-10-05.md)。
