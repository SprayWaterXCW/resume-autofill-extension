# 第二十三课：真实验收、语义校验与不能冒充成功的计数

## 这一步处在 Agent 的哪里

现在的流程是观察网页、取得模型建议、验证建议、执行、回读、复扫。问题出在验证与评估：先前只要输入后的值与资料一致，就可能将一次操作计为成功。这样能发现没有选中下拉选项、React 重渲染丢值等执行问题，但发现不了把正确资料写进错误的问题。

本轮真实测试发现：同一个期望薪资可以原样回读，却被写进当前薪资；同一段项目说明可以原样回读，却被写进本人职责。执行器工作与任务正确是两种不同证据。

## 三层检查

1. 来源检查：引用是否属于资料库、是否已确认、经历顺序是否正确。
2. 语义检查：问题与资料的概念是否相容。相近词不必完全相同；已知不同概念不能混用。
3. 执行检查：是否操作了当前文档的正确控件、是否选中并提交了控件内部状态、最终回读是否保持。

模型负责提出语义对应。确定性约束负责拒绝已知概念冲突。`field-semantics.js` 提供通用概念边界；规划器先用它约束可选来源，计划验证器独立检查，浏览器环境在写入前再次检查。这样即使模型忽略工具参数限制，也不会直接写入一个已经知道含义不符的来源。

这仍不是全面语义判定。没有被这些概念规则覆盖的问题，仍需模型判断、可信事实及真实评估。不能声称一组规则已经保证所有问题含义都正确。

## 为什么重渲染不能等同于任务变化

React 等界面会替换 DOM 节点。旧节点失去连接，只说明执行器需要重新取得节点。此前比较把页面所有按钮和没有字段的分组也纳入了条件，辅助结构变化可能让任务被误停。

现在比较填写目标：字段标签、类型、日期单位、记录索引、所属分组、禁用和只读限制。其他按钮不参与字段重取，添加经历的按钮仍使用新的观察和独立检查。字段含义或经历结构实际变化时，旧计划依然停止。

这属于基于语义身份的控件绑定恢复。它不允许凭 DOM 序号继续写一个新的问题。

## 为什么要保存差异而不是只保存错误名

`REAL_FORM_STRUCTURE_CHANGED` 说明比较失败，却不说明哪里不同。新的诊断只记录区域、编号、变化属性名和前后数量。比如 `datePart` 或 `entryIndex` 变化，与一个辅助 `control` 的出现需要不同修复。

本地执行日志自动通过现有 localhost 连接发送，使用封闭数据结构，去掉自由文本和资料值。日志失败不能中断填写。模型规划日志与浏览器执行日志现在可以用连接和运行 ID 对照。

## 局部修复与全局验证

一次区块建议冲突，不需要丢弃其他区块。规划器仅在同一快照的修复轮次缓存已得到的建议，依据校验错误中的字段和分组确定需要重做的区块。新快照、新的首次规划重新请求；最后合并的所有建议仍经过全局引用、记录顺序和语义校验。

这是减少无关重试的方式，不能以缓存代替完整验证。

## 写入归属与撤回

资料值与网页值相同，不足以证明网页内容由 Agent 写入。安全撤回需要当前文档的私有凭据：来源路径、字段身份和当时写入后的值均能重新核对。凭据保留在扩展隔离环境的 WeakMap 中，不进入执行日志。

扩展重载或页面导航可能销毁隔离环境。凭据消失后，既有内容与不相容的资料恰好相同，只能被标为语义疑点；不能自动当作 Agent 所有。真实本轮就遇到了这个限制，留下 3 处待核对内容。

## 真实验收的标准

本轮用户明确要求只点击开始，资料和模型配置使用现状。维护更新之外，没有预扫描、清空页面、手工补填或换一个配置来获得更好的结果。

报告必须列出真实新增、已有内容、未规划、空白和语义疑点。代码回归通过只能证明所测试的协议与边界，不能证明真实网站可用。在已有内容的页面继续运行，也不能冒充从空白表单开始的验收。
