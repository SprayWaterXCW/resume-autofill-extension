# 规划引用错误检查与修复

日期：2026-10-05；扩展：0.6.6；网站：用户选定的京东方简历编辑页。

本报告只记字段标签、资料路径、错误代码和计数，不保存简历值、完整页面地址或模型原始响应。

## 1. 修复前的证据

Chrome 扩展面板的最后一轮执行有 59 个字段、8 个分组、142 个资料路径；三次规划失败后停止。没有开始本轮表单写入，网络保护已自动解除。

后台日志与面板顺序一致：

| 次数 | 错误 | 可确认的问题 |
| --- | --- | --- |
| 1 | `PLAN_DUPLICATE_REFERENCE` / `source_in_multiple_fields` | `awards.0.name` 同时用于 `field-44`、`field-45`，即奖项和获奖描述 |
| 2 | `PLAN_UNKNOWN_REFERENCE` | 原日志没有引用种类或目标，不能还原是哪条未知引用 |
| 3 | `PLAN_DUPLICATE_REFERENCE` / `source_in_multiple_fields` | `languages.0.testScore` 同时用于 `field-22`“英语等级成绩”和 `field-23`“其他语言能力及等级/分数” |

这些错误发生在计划校验阶段。该轮没有出现模型超时；不能用网络问题解释这次停止。更早的教育分组冲突和期望城市重复引用属于其他日志记录，不能混成同一轮。

## 2. 修改

- 原生函数的 JSON Schema 列出当前允许的分组 ID、字段 ID、资料区块和资料路径枚举；运行时依然执行独立校验。
- 提示说明英语成绩与其他语言、奖项名称与描述、个人简介与兴趣、证书与论文的区别，缺少来源时留为未解决。
- 模型重试接收已确认的多个错误，包含本轮较早失败及同一建议中其他已定位的问题。
- 最多三次模型调用。最后仍失败时，可以构造局部计划：删除全部冲突引用；不会任意保留一个重复目标，也不会更换事实来源或调整记录顺序。
- 局部计划在后台和调用方分别重新通过完整校验，执行前再观察页面；页面变化仍停止。
- 未知引用诊断区分 `unknown_field`、`unknown_source`、`unknown_group`、`unknown_section`，只附已存在的引用。后台日志增加 UTC 时间、连接 ID、请求 ID、快照摘要和耗时。
- 页面诊断显示字段 ID，方便把错误记录对应到网页标签。面板与复制记录显示版本 0.6.6。

## 3. 验证

`npm test`：86 项通过。新增回归覆盖：

1. 未知字段、路径、分组和区块的诊断不包含模型编造的原始文字。
2. 两个目标共用成绩时，两者都隔离；其他合法手机号映射保留。
3. 同一教育记录分配到两个分组、跨记录串填都不能通过局部计划获得授权。
4. 三次失败后才使用局部计划；重试反馈保留多种错误；日志不含虚构私有值。
5. 第三次规划返回时页面已变化，仍在任何写入前停止。

规划 WebSocket 往返测试另检查了“后台拒绝 → 传递脱敏局部建议 → 调用方核验 → 仅执行其余合法字段”的组合路径。该测试使用虚构数据和模型替身。

`npm run build:extension` 成功。普通 Chrome 的扩展管理页确认当前已安装版本为 0.6.6；权限没有新增。项目自己的本机模型服务已重启加载新代码。

## 4. 真实网站结果

使用原有已导入的 142 条资料目录，在用户已授权的京东方页面完成一次实际运行：

| 指标 | 结果 |
| --- | --- |
| 模型请求 | 1 次 |
| 计划关联 | 28 / 59 个初始字段 |
| 最终回读保留本轮写入 | 14 个字段 |
| 新增经历 | 0 组 |
| 计划中的经历缺口 | 13 组；获奖与竞赛合并为 10 条记录 |
| 未完成控件或回读失败 | 13 个 |
| 保留、未映射或缺少资料的字段 | 31 个 |

这次计划一次通过，未触发三次失败后的局部计划。局部计划机制由上述故障回归和 WebSocket 组合测试验证。不能把本次成功的 14 个回读结果描述成整份简历语义完全正确。

实际执行记录仍有 `OPTION_UNAVAILABLE`：籍贯、可面试城市、期望薪资以及教育、实习、在校职务的日期未完成。页面的非原生“添加”控件尚未识别，记录缺口仍在。论文名称出现 `READBACK_MISMATCH`。证件号码最初回读成功，在整页最终复核时发生变化，成功计数已经撤回；不能认定其当前内容正确。

没有点击保存草稿、预览并提交、投递或等价最终动作。任务结束后保留本轮页面保护，等待用户检查；需要手工操作时点击“恢复正常浏览”，以免刷新丢失未保存的填写内容。

## 5. 下一步

按已观察到的失败补控件能力：先验证京东方的新增经历控件，再做日期和地区选择；每种能力都需要观察实际选项与提交结果到控件的回读，不能仅靠输入了文字就计作成功。证件号码的最终变化还需要专门的事件级诊断，当前记录只支持判定最终核验失败，不支持推断具体清空原因。
